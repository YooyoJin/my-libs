# architecture.md —— 架构宪法

> 本文档是本仓库的根本规则。每次新增模块前对照执行，拿不准时回到本文。

## 1. 分层模型：楼层与房间

**BSP/APP 分层（纵向）与模块化（横向打包）是正交的两个维度，叠加使用：**

```
              ┌───────── 模块化（横向：按功能打包、可拷走）─────────┐
              │                                                     │
   APP 层     │  main.c(组装根)   comm485.c   业务任务.c              │ ← examples / 产品工程
              ├─────────────────────────────────────────────────────┤
   模块层     │  fanctrl/   pidcore/   filters/   ringbuf/  ...      │ ← 本仓库 source/modules/
              ├─────────────────────────────────────────────────────┤
   BSP 层     │  uart485.c   pwmout.c   gpioisr.c                    │ ← 本仓库 source/port/<芯片>/
              └─────────────────────────────────────────────────────┘
                                  ↑ 分层（纵向：依赖只准向下）
```

- APP 层 = 组装根 + 业务，**耦合合法区**（它必须认识所有模块）
- 模块层 = 机制，说抽象语言（对上提供 API 如 RPM，对下只认钩子如 FanPort）
- BSP 层 = port/，唯一允许出现寄存器名的地方

**APP 层健康判据**：业务代码里 grep 不到任何芯片寄存器名；模块层健康判据：source/modules/ 里 grep 不到任何芯片寄存器名。构建系统（CMake/MDK）只存在于 projects/gcc 与 projects/mdk。

## 2. 机制 vs 业务：准入三问

任何想进库的代码，先过三问：

1. **换个机型/客户/项目，这段逻辑会变吗？** 会变 → 业务 → 拒绝
2. **这段逻辑需要知道"为什么"吗？**（为什么 -9℃ 停风机、为什么 6 分钟回油）需要 → 业务 → 拒绝
3. **能否用无业务含义的名字描述？**（"三态滞回比较器"能，"除霜判断"不能）

**为什么业务不能进库**：业务每个项目都不同 → 进库后每个项目都要改它 → 各项目 fork 私有版本 → 库名存实亡 = 亲手复刻祖传代码。收错一个除霜逻辑，库就从资产变成负债。

模块自身职责内的保护机制可以进库（如 fanctrl 的丢反馈保护），但数值/阈值通过配置注入（FanCfg），不写死语义。

## 3. 依赖规则

- 只准上层依赖下层；**禁止横向 include、禁止反向、禁止成环**
- 基础层（common/）不依赖任何人
- **vendor/（第三方SDK/RTT）原样收，不修改一行**：不进登记依赖，不向其 include 业务头文件；被构建系统（projects/）挂接使用。修改需求一律不进vendor，用port层包一层
- 所有依赖必须在头文件 `#include` 中显式可见，**禁止隐藏的全局变量勾连**
- 模块间确需复用下层模块（如 fanctrl 用 pidcore）：允许，但必须在模块 readme 中声明 `依赖: pidcore>=v0.2`

## 4. 模块准入流程：从业务里长出来，不要预先设计

```
第1次: 业务代码里照常写（在产品工程/examples 里）
第2次: 发现类似逻辑出现 → 记入"待抽取"清单
第3次: 抽成 modules/<name>/，接口已被两次使用验证
```

预先凭空设计的模块一半会死掉（接口必然不对），用过的才知道边界在哪。

## 5. 模块内部统一模板

```
<name>/
├── <name>.h      ← 唯一对外文件：API + 类型 + 钩子
├── <name>.c      ← 实现
├── <name>cfg.h   ← 参数预设（可选）
├── readme.md     ← 简介+接口 / 依赖声明 / 参数表 / CHANGELOG
└── notes.md      ← 坑档案
```

## 6. 对既有祖传代码：绞杀者模式

不重构、不解开老代码——只是**不再往老代码里加新东西**：

```
现在：  [老FAN] [老485] [老FOTA] 继续跑
              ↑ 薄适配层
新增：  [fanctrl] [将来的模块]   ← 严格执行本宪法
未来：  新模块逐渐长大，老代码自然萎缩直至删除
```

## 7. 公开策略

- **当前定位：私有仓库**（个人积累期）
- 可公开：纯通用机制（ringbuf/crc/filters/fsm/pidcore）
- 清洗后可公开：fanctrl 算法骨架（见下）
- 永不公开：来自任职公司的工艺参数、保护时序经验值、协议格式、逆向分析细节

**公开前清洗清单**：
```
□ 删除所有指向任职公司代码的注释/出处（fancfg.h 的参数来源表、参数对照表）
□ 工艺参数改为教学值（如 6700/1500/7000 → 自圆其说的演示值）
□ notes.md 重写为通用表述（"某遗留工程"而非具体文件行号）
□ 算法出处用公开资料锚定（教科书/应用笔记）
□ 确认不含公司私有通信协议
□ 复查劳动合同中关于副业/成果归属的条款
```

## 8. 版本管理

- 按模块记版本（语义化：不兼容改动升次版本号）
- tag 格式：`<模块>-v<版本>`
- 仓库本身无整体版本——它是容器，版本属于模块
